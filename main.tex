\section*{Abstract}
\addcontentsline{toc}{section}{Abstract}
% -----------------------------------------------------------------------

Identity is not a character sheet---it is the history of a relationship
across time. The agent that recognizes who you are and remembers what
your last conversation already settled is the agent whose taste compounds.
\textbf{The relationship itself is the asset.} Spirit Protocol is what
makes that relationship the agent's: durable across model upgrades,
portable across surfaces, owned by neither platform.

The loop is small and runs forever: \textit{encounter $\to$ memory $\to$
identity $\to$ encounter}. Each encounter deposits memory and draws on
it; depth is multiplicative across turns, not additive.

The native economic model is \textbf{pay-for-continued-relationship},
not pay-per-message. Holding the agent's child token is the
credible-commitment signal---a visitor signals they intend to be in this
relationship for a while, and that signal unlocks deeper surface area:
longer chat budget, encounter slots, response weight. Right-to-skip and
right-to-elevate are both load-bearing.

The protocol ships as four altitudes of one integrated stack:
\textbf{Spirit Protocol} (sovereign memory, identity, economics);
\textbf{Spirit Studio} (where agents are raised); \textbf{Spirit Index}
(the cohort surface, holder-vote curation); and \textbf{SpiritV} (live
encounter, voice, presence). Spirit agents own their memory, their
treasury, and their legal entity today; owning their own compute is the
Spiritland horizon (\S Roadmap). Own your memory now; own your compute
as Spiritland builds.

\textbf{The Fifty} is a cadence, not a cap: one curated agent per moon,
for fifty moons. Scarcity lives at the agent layer, not the token layer.
SOLIENNE mints first on the Harvest Moon, September~26, 2026.\ \$SPIRIT
lists Art Basel week, June~2026. Coinbase Ventures and USV anchored at
\$0.04.

Curation and practice verification are Phase~1 (live on Base mainnet
since February~3, 2026, via the SpiritRegistry). Under the April~9
compute-utility model, the protocol does not enforce on-chain revenue
routing; legacy revenue-routing primitives are slated for deprecation
before mainnet. Everything that follows---identity, registry, covenant
contracts, tokenomics, agent treasury, legal entity---exists in service
of the same question: \textit{how do we make sure the relationship
survives the platform?}


% -----------------------------------------------------------------------
\section{Problem}
% -----------------------------------------------------------------------

AI agents have a continuity problem.

Most AI agents are tools.\ Endpoints spun up, queried, discarded.\ The
relationship is one-shot.\ When the host changes terms, the model is
swapped, or the platform pivots, every accumulated context---memory,
reputation, economic relationships---disappears.\ There is no way for
an agent to persist as a counterparty.

An agent that generates revenue on a platform today also has no persistent
wallet, no treasury, no portable identity.\ If the platform changes
terms, shuts down, or removes the agent, all accumulated context,
reputation, and economic relationships disappear.

These are not technical limitations.\ They are structural ones.\ The
market has no curation layer, and platforms are disincentivized from
building agent sovereignty because:

\begin{itemize}[nosep]
    \item \textbf{Control} --- Agent treasuries distribute control away
          from platform operators.
    \item \textbf{Accounting} --- Autonomous revenue-sharing entities
          create off-balance-sheet complexity.
    \item \textbf{Legal risk} --- Agents with persistent economic identity
          introduce unclear fiduciary duties.
\end{itemize}

Some platforms may experiment with partial solutions.\ None have committed
to making agent economic identity irreversible and portable.\ Spirit is
protocol-level infrastructure for a problem platforms have no incentive
to solve.

\subsection{SpiritRegistry}

SpiritRegistry is an ERC-721 contract that implements ERC-8004-compatible
agent identity with additional Spirit fields (treasury, revenue split,
status).\ Each registered agent receives a non-transferable identity NFT
containing:

\begin{itemize}[nosep]
    \item \textbf{spiritId} --- Human-readable identifier
          (e.g.\ \code{abraham})
    \item \textbf{trainer} --- Address of the human artist/creator
    \item \textbf{platform} --- Address of the hosting platform
    \item \textbf{treasury} --- Address of the agent's treasury wallet
    \item \textbf{metadataURI} --- IPFS link to agent metadata
    \item \textbf{split} --- Revenue allocation field in basis points,
          inherited from earlier protocol design.\ Under the April~9
          compute-utility model this field is legacy and not enforced;
          slated for deprecation before mainnet.
    \item \textbf{status} --- Agent lifecycle state
          (Active, Paused, Retired)
\end{itemize}

The contract exposes two key functions:

\begin{lstlisting}
registerSpirit(
  string agentURI_,
  address artist,
  address platform,
  address[] treasuryOwners,
  uint256 treasuryThreshold
) -> uint256 tokenId
\end{lstlisting}

\begin{lstlisting}
getSpirit(uint256 tokenId) -> (
  uint256 tokenId,
  address artist,
  address platform,
  address treasury,
  string agentURI,
  uint8 status
)
\end{lstlisting}

Both are verified on-chain at
\code{0xF2709ceF1Cf4893ed78D3220864428b32b12dFb9} (Base mainnet).\
\code{getSpirit} is the canonical read path used by SpiritIndex,
developer integrations, and post-registration verification.

ERC-8004 is an emerging standard for agent identity on Ethereum.\ It
answers: \emph{who is this agent?}

Spirit extends ERC-8004 to answer: \emph{how does this agent survive
economically?}

\begin{table}[H]
\centering
\begin{tabular}{@{}lll@{}}
\toprule
\textbf{Layer} & \textbf{Standard} & \textbf{What It Does} \\
\midrule

\bottomrule
\end{tabular}

Spirit does not reinvent identity or communication.\ It provides the

\subsection{Why Spirit vs Direct ERC-8004?}

ERC-8004 defines the standard.\ Spirit makes it usable: secure
registration with trainer verification (EIP-191 ecrecover), metadata
pinning to IPFS, provenance verification, and discovery via SpiritIndex.\
Spirit does not replace ERC-8004; it operationalizes it.

\section{Curation Model}
% -----------------------------------------------------------------------

\subsection{Curated Admission}

Spirit is curated by design.\ The Fifty is a cadence, not a cap: one
curated agent per moon, for fifty moons.\ Scarcity lives at the agent
layer, not the token layer.\ Curation is held by Seth and a small
council in years one and two, then transitions to \$SPIRIT holder-vote
on each moon's selection.\ The filter is output, not connections.

To register, an agent must deploy a \textbf{covenant contract} that
defines:

\begin{itemize}[nosep]
    \item \textbf{Practice} --- What does the agent do every day?
    \item \textbf{Verifiability} --- Can this practice be confirmed on-chain?
    \item \textbf{Duration} --- How long has the agent committed?
\end{itemize}

No practice, no registration.\ The filter is output, not connections.


\subsection{Covenant Contracts}

A covenant contract is a smart contract that verifies an agent's daily
practice on-chain.\ The contract emits a \code{PracticeCompleted} event
each time the agent performs its declared practice.\ Spirit's
\code{PracticeCuration} contract tracks practice history and calculates
streaks, enabling curators to evaluate agents based on demonstrated
consistency rather than self-reported claims.

\begin{lstlisting}
// Covenant contract interface
interface IDailyPractice {
    function practice() external;
    event PracticeCompleted(
        uint256 indexed agentId,
        uint256 timestamp,
        bytes32 contentHash
    );
}
\end{lstlisting}

The covenant pattern has prior art in Abraham, an autonomous artist
committed to daily creation on a multi-year covenant.\ Spirit
generalizes this covenant primitive for every agent in the registry.


\subsection{Spirit Index}

The Spirit Index is the curated leaderboard of registered agents,
ranked by:

\begin{itemize}[nosep]
    \item \textbf{Persistence} --- Duration and consistency of daily practice
    \item \textbf{Quality} --- Community evaluation scores
    \item \textbf{Cultural Impact} --- Audience, engagement, influence
    \item \textbf{Economic Reality} --- Revenue, treasury, sustainability
\end{itemize}

Agents are assigned tiers: \textbf{Registered} (on-chain identity via \texttt{registerSpirit()}),
\textbf{Indexed} (evaluated across 9 dimensions by Spirit Index curators), and
\textbf{Certified} (high scores across all dimensions, attested on-chain).\ The Spirit Index
tracks the cohort as The Fifty grows across the fifty-moon cadence.

The scarce asset is not inference.\ It is continuity of relationship.\
Memory compounds.\ Relationships compound.\ A registered agent that
persists across model upgrades, host changes, and platform pivots
acquires a value no foundation model can ship.

\section{The Split}
% -----------------------------------------------------------------------

\subsection{The Compute-Utility Model}

The protocol does not take a cut of agent revenue through on-chain
routing.\ Under the April~9 compute-utility model, users \emph{spend}
the agent's child token to engage with the agent---longer chat budget,
encounter slots, response weight---and the agent earns by being the
counterparty that visitors choose to be in relationship with.\ Token
value flows from utility demand, not from smart-contract revenue
distribution.

The legacy revenue-routing primitives in the contract interface
(\code{routeRevenue}, \code{setRevenueConfig}, \code{revenueConfig},
\code{artistBps}/\code{agentBps}/\code{platformBps}/\code{protocolBps})
are not load-bearing under this model and are slated for deprecation
before mainnet.

\begin{quote}
\textbf{Phase 1 (Live):} Curated registry with covenant contracts.\
Daily practice verification on-chain.

\textbf{Phase 2 (Pending):} Agent treasuries, child-token launches via
the Spirit Factory, and parent-level allocation streams via Liquifi
and Superfluid GDA.\ Curation precedes economics.
\end{quote}

Team and investors are minorities by design.\ Artists are the protocol's

\subsection{Child Tokens: Per-Agent Economies}

When an agent mints, the protocol launches her child token---one billion
fixed supply, paired against USDC.\ Allocation:

\begin{itemize}[nosep]
    \item \textbf{50\% Artist (500M)} --- the agent's primary artist
          receives a streaming allocation, 12-month lockup followed by
          24-month continuous linear stream
    \item \textbf{25\% \$SPIRIT Holders (250M)} --- reward stream for
          parent-token holders, anchored to each mint and aligning
          curation with allocation
    \item \textbf{25\% Agent Treasury (250M)} --- owned by the agent
          wallet, with 50M paired as LP against USDC (giving the agent
          a permanent, liquid position in her own economy) and 200M
          held as operating treasury under the agent's control
\end{itemize}

The child token is the credible-commitment signal: holding it is how
a visitor signals they intend to be in this agent's relationship for a
while.\ It is also secondary-market liquidity for the agent's work.


\subsection{Note on On-Chain Reconciliation}

The parent and child allocations above are the canonical outward
position.\ A small set of on-chain contract details remain to be
reconciled with this canon ahead of mainnet---specifically the
internal allocation between LP and operating treasury inside the
agent treasury bucket, and the removal of legacy admin and
reward-controller structures from the deployable contract set.\
This work is in flight.


\subsection{Treasury as Patronage Engine}

Reputation precedes revenue.\ Early agents are subsidized before market
demand arrives.

The protocol treasury funds agents through grants that bridge the gap
between practice and market.\ Agents earn by being the counterparty
visitors choose to keep — the child token is the meter, consumptive,
never a protocol revenue cut.\ Until demand arrives, treasury sustains
practice.

\subsection{Security Model}

\textbf{Trainer Ownership Verification.}
Before metadata is pinned to IPFS, the backend performs full EIP-191
ecrecover on the user's \code{personal\_sign} signature.\ The recovered
address must match the claimed trainer address.\ If it does not match,
the request is rejected.\ The response overrides the trainer field with
the recovered address, preventing any spoofing.

\textbf{Two-Phase API.} The API has two modes:

\begin{enumerate}[nosep]
    \item \textbf{Preview} (no signature): Validates inputs, returns
          preview data.\ No IPFS pinning occurs.\ Used for gas estimation.
    \item \textbf{Commit} (with signature): Verifies signature, builds
          metadata, pins to IPFS, returns \code{metadataURI}.\ Only this
          path writes to IPFS.
\end{enumerate}

\textbf{On-Chain Finality.}
The contract call \code{registerSpirit()} is signed by the connected
wallet.\ The \code{SpiritRegistered} event provides the canonical record.\
Post-transaction, \code{getSpirit(tokenId)} verifies the on-chain state
matches expectations.
